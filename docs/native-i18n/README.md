# Native internationalization migration

Status: approved and in progress; the original proof, complete 15-route `/breathe` family, and complete 19-route `/for` family are available in local `native-preview`; production remains on the proxy path  
Started: 2026-07-15  
Locales in scope: English, Spanish, Brazilian Portuguese, French, German, Japanese

This directory is the durable working record for moving localization into the Deep Breathing repository. Keep it current as implementation progresses. The roadmap records what remains, the decision log records why the architecture looks the way it does, and the progress log records what actually happened.

## Objective

Make this repository the complete source of truth for translated content and serve every localized page natively from Next.js.

The migration is successful when:

- `deepbreathingexercises.com` no longer needs MassTranslate in the request, build, deploy, or content-authoring path.
- English and localized pages are rendered from repository-owned content on the server.
- Browsers and crawlers receive the same localized page content.
- The current public URLs, canonicals, and locale prefixes remain stable.
- Local development and preview deployments can render every supported language without external translation infrastructure.
- Translation coverage, staleness, metadata, and route availability are deterministic and testable before deployment.
- Adding or maintaining a language is ordinary repository work rather than a proxy integration project.

This is a foundation and technical-debt project. A search-ranking increase would be welcome, but it is not required to justify the work.

## Non-goals

The initial migration does not include:

- Adding a new language.
- Rewriting or materially improving the imported translations.
- Selecting a future translation vendor, model, keyword tool, or authoring UI.
- Doing keyword research or changing target keywords.
- Renaming existing routes, locale prefixes, or English URLs.
- Redesigning pages or changing breathing-session behavior.
- Upgrading Next.js or replacing unrelated application architecture.
- Combining the migration with unrelated SEO experiments.
- Keeping MassTranslate as a fallback translation service after cutover.

Translation quality problems discovered during import should be recorded. Fix only errors that block safe native rendering, and keep broad editorial review as separate follow-up work.

## Current architecture

The English Next.js application is the origin. MassTranslate currently sits in front of it as an edge reverse proxy for locale-prefixed requests.

```text
Localized request
    -> MassTranslate edge proxy
    -> locale prefix stripped
    -> English Next.js origin
    -> proxy-selected translation behavior
    -> localized response
```

Important current behaviors:

- Recognized crawler user agents can receive translated server HTML.
- Browser requests receive English HTML followed by a client-side translation pass.
- `window.__MT_CONFIG__` helps client code infer locale and the underlying English path.
- The repository manufactures locale URLs and hreflang entries in the sitemap even though Next.js does not own those localized routes.
- The language switcher is client-gated to avoid proxy link rewriting and double-locale URLs.
- A two-hour cache warmer protects locale pages from 5 to 21 second cold responses after deployments.
- Signed inbound webhooks use the `origin.` hostname because the apex proxy can invalidate request signatures.
- Localized Open Graph titles are generated by scraping translated production pages.
- A small set of interactive runtime phrases already lives in the repository, separately from the long-form page translations.

This arrangement proved the value of localized pages, but it has also produced recurring failure classes:

- English first paint and delayed translation in browsers.
- Hydration mismatches caused by translation-time DOM mutation.
- Half-English pages when source copy changes and text matching no longer succeeds.
- Different HTML for crawlers, browsers, command-line checks, and query-string variants.
- Cross-locale links and redirects that depend on proxy rewriting details.
- Canonical and hreflang discrepancies that cannot be reproduced locally.
- Cold-cache crawler timeouts and the operational need for a locale cache warmer.
- Proxy-specific exceptions for signed requests and social metadata.

The current operational details remain documented in [`../runbooks/tools-and-data-sources.md`](../runbooks/tools-and-data-sources.md) until cutover is complete.

## Target architecture

The Next.js application will own locale detection, routing, content selection, rendering, and SEO output.

```text
Localized request
    -> Next.js locale route
    -> repository-owned route manifest
    -> checked-in route and shared bundles
    -> localized server HTML
    -> hydration using the same localized data
```

The target has five logical parts:

1. **Locale registry**
   Defines supported locale tags, public prefixes, language names, direction, fallback policy, and publication state in one place.

2. **Route manifest**
   Defines which routes exist for each locale and which translation bundle they require. Sitemap, hreflang, static generation, and the language switcher consume the same manifest.

3. **Checked-in translation bundles**
   Long-form page copy and page-specific metadata are stored per route and locale. Reused navigation, breathing controls, settings, and authentication labels live in a small shared bundle.

4. **Native server rendering**
   Locale-prefixed routes render localized HTML directly. Client components receive the same localized values as the server, so hydration does not require DOM mutation.

5. **Build-time validation**
   Published locale-route pairs must have complete, valid bundles. Missing or stale required content fails the build or keeps the route unpublished. Public localized pages never silently fall back to English.

The exact filesystem layout may evolve during the foundation phase, but it must preserve route ownership and deterministic loading. The implemented `/breathe` boundary is:

```text
src/i18n/
├── route-manifest.ts
└── content/
    ├── bespoke/breathe-index/
    │   ├── messages/
    │   ├── publication.json
    │   └── server/
    └── breathe/
        ├── manual/
        ├── reviewed-replacements/
        ├── routes/
        ├── chrome/
        ├── provenance/
        ├── unresolved/
        ├── publication.json
        └── server/
```

The `/for` family reuses the same boundary with `bespoke/for-index/` for its hub and `use-cases/` for its eighteen structured routes. The file extension and schema are implementation details. The architectural requirements are typed access, deterministic diffs, route-level loading, placeholder validation, and no production network fetch for translations.

## Content lifecycle after migration

1. English content is edited in the repository.
2. Stable message IDs remain unchanged when wording changes.
3. A source hash marks affected translations as stale.
4. The route stays on its last-known-good translated bundle until an intentional update is approved, or it is held out of publication if no safe bundle exists.
5. Translation changes are reviewed and deployed through normal Git workflows.

The future translation tool can be manual, scripted, or external. It must write reviewable repository files and cannot become a runtime dependency.

## Owner checkpoints

No owner action is required for the repository foundation, catalog mapping, semantic bundle work, shared renderer refactors, or native preview implementation.

Owner decisions recorded on 2026-07-15:

1. **Translation closure is approved:** Luna may translate content that cannot be recovered unambiguously from the preserved catalog. The generated bundles must still pass semantic, placeholder, markup, safety, and completeness validation before publication.
2. **Production cutover is approved:** no further owner approval is required once the preview matrix, crawl, performance, external-state inventory, and rollback rehearsal gates pass. This authorization does not bypass those gates.
3. **Migration and improvement are separate:** preserve existing English meaning during native migration, repair only missing or objectively broken translations, and evaluate content, evidence, or SEO improvements as later measurable changes.

Explicit owner input is still required for **external cleanup**, meaning permanent removal of the MassTranslate Worker configuration, credentials, cache jobs, and rollback path after the observation window.

The cutover phase also needs confirmed access to Cloudflare routing, Vercel production configuration, signed-webhook destinations, and any external monitors. Capture and verify that access during the external-state inventory rather than waiting for cutover day.

## Definition of done

The migration is complete when:

- All currently published locale-route pairs render native localized HTML.
- The repository contains every translation required to build and serve them.
- Local, preview, and production behavior agree without MassTranslate credentials or network access.
- Automated tests cover routes, coverage, metadata, canonicals, hreflang, sitemap membership, links, placeholders, and hydration.
- Search engines retain the current public URLs without a migration-induced indexing regression.
- Proxy-only cache warming, DOM translation, link rewriting, metadata scraping, and request exceptions are retired or explicitly retained for a non-translation reason.
- Production has completed the observation window and the external proxy can be disabled without losing a rollback artifact.
